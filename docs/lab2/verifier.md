# Верифікатор на іншій моделі

## Конфігурація

- Модель, що писала код: Anthropic Claude Opus 5.5 (`claude-opus-5-5`) у Claude Code 2.1.269 — весь код Лаб. 2, зокрема сам верифікатор.
- Модель верифікатора: OpenAI `gpt-5.6-terra` (Chat Completions, `response_format: json_object`; ціна $2 / $12 за 1 млн токенів — звірено зі сторінкою OpenAI 2026-10-31, збігається з `src/models.ts`). Інший провайдер і інша родина моделей, ніж автор коду. Задається `VERIFY_MODEL` ([`.env.example`](../../.env.example)), у CI — у [`verifier.yml`](../../.github/workflows/verifier.yml).
- Чому саме ця: ключ OpenAI вже є (Лаб. 1); методичка радить починати із сильного судді — найсильніша `gpt-5.6-sol` удвічі дорожча, `gpt-5.6-luna` — та сама модель, що відповідає в базовій лінії. Вибір terra — рішення власника репозиторію як компроміс ціни й сили.
- Де брама:
  - CI на пул-реквестах у `main` — [`.github/workflows/verifier.yml`](../../.github/workflows/verifier.yml); ключ — секрет репозиторію `OPENAI_API_KEY`. Червоний = хоча б один `fail`.
  - Локально перед злиттям: `bash scripts/lab2/make-diff.sh main...HEAD > docs/lab2/verify-input.diff`, потім `npm run verify` (ключ через `--env-file`).
  - Щоб червоний job технічно не давав злити, у GitHub → Settings → Branches для `main` треба увімкнути «Require status checks» з job «Верифікатор (gpt-5.6-terra проти spec.md)» — це налаштування робить власник репозиторію.
- Код: схема [`src/verify/schema.ts`](../../src/verify/schema.ts), суддя [`src/verify/judge.ts`](../../src/verify/judge.ts), скрипт [`scripts/verify.ts`](../../scripts/verify.ts), тести [`tests/lab2/verify.test.ts`](../../tests/lab2/verify.test.ts) (без мережі, на підробленій моделі).

## Рубрика

Один критерій — один окремий запит (суддя бачить лише цей критерій). Невалідна за схемою відповідь перепитується один раз, потім скрипт падає (код 2). Перед відправкою diff фільтрується: файли секретів викидаються, рядки, схожі на ключі API, маскуються, вміст `data/` і журналів агента стискається до заголовків і розміру; еталонний набір іде з повним контекстом файлу ([`make-diff.sh`](../../scripts/lab2/make-diff.sh)).

Системний промпт судді — `JUDGE_SYSTEM` у [`judge.ts`](../../src/verify/judge.ts); запит користувача — дослівно `Критерій <id>: <твердження>` / `Чим перевіряється: <…>` / (довідка) / diff.

| Критерій зі spec.md | Що питаємо суддю (дослівно, з розділу 6) | Що вважається evidence |
|---|---|---|
| A1 | «`npm test` зелений, зокрема тести валідатора еталонного набору» · «прогін CI» | результат прогону в diff; на практиці майже завжди `unknown` — diff результатів не містить |
| A2 | «`docs/lab2/golden/queries.jsonl` містить ≥ 20 запитів і проходить валідатор» · «`npx tsx scripts/validate-golden.ts`» | рядки `queries.jsonl` у diff (повний файл); `fail`, якщо їх < 20 |
| A3 | «у eval-report.md точність на еталонному наборі ≥ 60%» · «перевіряється числом у файлі» | число в `eval-report.md` у diff; до кроку 06 файлу немає → `unknown` |
| A4 | «у data/obd/ лежать усі 23 документи» · «скрипт перевірки повертає 0» | перелік файлів `data/obd/*.md` у diff проти довідки з id розділу 2 (додано після калібрування 2) |

### Що змінено після калібрування

1. Після прогону 1 — промпт судді (`a935c10e`): «якщо diff містить УСІ дані, які перевіряє команда, і з них видно, що твердження виконується, — pass; відсутність результату запуску сама по собі не підстава для unknown», і «числа бери із самого твердження». **Не допомогло**: прогін 2 — 52/55. Причина виявилась не в рубриці, а у вхідних даних.
2. Після прогону 2 — вхідні дані судді (`da11c4a5`): заглушка стиснутих файлів тепер пише розмір; у запит додано довідку з id 23 документів розділу 2; еталонний набір іде з повним контекстом файлу (`make-diff.sh`, той самий у CI й калібруванні). Ручну розмітку не змінено.
3. **Зміни п. 2 не відкалібровані**: власник вирішив не робити третій прогін (≈ $0.7) і чесно зафіксувати розходження. Брама в CI працює вже з цими змінами. Перевірити їх — перший пункт, якщо знадобиться перекалібрування: очікування — c02/A4, c05/A2, c11/A4 стають `pass`, c03/A4 лишається `unknown`, c04/A2 — `fail`.

Вартість калібрування: прогін 1 ≈ $0.69, прогін 2 ≈ $0.71 (по 55 запитів до `gpt-5.6-terra`).
