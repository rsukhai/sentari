# Верифікатор на іншій моделі як остання брама — Лабораторна 3, крок 02

**Пара «виконавець — верифікатор»: Claude Code (`claude -p`, Anthropic, `sonnet`) → `gpt-5.6-terra` (OpenAI). Брама стоїть у CI** (задача `verify`, ключ — секрет репозиторію `OPENAI_API_KEY`).

## Місце в ланцюзі

- Детерміновані брами (крок 01): `types → lint → tests → build` — [`gates.md`](gates.md).
- Верифікатор запускається лише після них: задача `verify` у [`gates.yml`](../../.github/workflows/gates.yml) має `needs: build`. У її `if:` немає функції статусу, тож діє неявний `success()`: на червоній детермінованій брамі `verify` не стартує (`skipped`).
- Бігає лише на гілках прогонів фабрики (`harness/t-NN…`). На `lab3/*`, `main` і навмисно червоній `harness/red-…` — `skipped`.
- Економія: **поки що фактично нуль.** З 9 прогонів `gates` (8 завершених, один скасовано `concurrency`) лише один червоний на детермінованих брамах — навмисний `harness/red-2026-11-08`, а його ім'я `verify` і так не запускає. Тобто жодного реального прогону верифікатора `needs` нам ще не заощадив. Механізм той самий, що показує `skipped` для `lint/tests/build` у [прогоні 42494757155](https://github.com/rsukhai/sentari/actions/runs/42494757155); ціна одного прогону верифікатора, яку він би не отримав, виміряна: **≈ $0.051** (18 159 / 1 217 токенів на 8 критеріїв).

## Конфігурація

- Модель, що виконувала задачу: Anthropic, Claude Code, `--model sonnet` (див. [`factory.md`](factory.md)).
- Модель верифікатора: OpenAI, `gpt-5.6-terra` ($2 / $12 за млн токенів, [`src/models.ts`](../../src/models.ts)). Та сама, що в Лаб. 2, але промпт інший.
- Шлях і його ціна: платний OpenAI, ключ уже був у репозиторії. Калібрування (42 критерії) — $0.2052; прогін у CI на 8 критеріях — ≈ $0.051.
- **Інша родина — перевіряється кодом, а не словами:** `assertOtherFamily(executorProvider('claude-code…'), 'openai')` у [`verify-task.ts`](../../scripts/harness/verify-task.ts); модель з тієї самої родини → відмова, а не попередження. Модель задається `VERIFY_MODEL` ([`.env.example`](../../.env.example)), ключа в репозиторії немає.
- Умова блокування: червоно, якщо хоч один критерій не `pass` — `isBlockedStrict` у [`src/verify/schema.ts`](../../src/verify/schema.ts). `unknown` теж блокує. Старий `isBlocked` (блокує лише `fail`) лишено для Лаб. 2 і в харнес не перенесено.
- Схема вердикту строга (`id`, `verdict`, `reason`, `evidence`, zod `.strict()`): невалідну відповідь перепитують один раз, далі код виходу 2.
- Один суддя — один вимір: окремий запит на кожен критерій задачі.

## Рубрика — один запит на один критерій

Критерії — поле `criteria` у [`tasks.jsonl`](tasks.jsonl) (42 на 8 задач). Для t-08 є ще `context`: перші 25 рядків чотирьох скриптів, на які посилається README. Системний промпт — `TASK_JUDGE_SYSTEM` у [`src/verify/task.ts`](../../src/verify/task.ts), версія 1; після калібрування не змінювалась.

| Тип критерію | Що питаємо суддю | Що вважається evidence | Що означає unknown |
|---|---|---|---|
| «Тест перевіряє X» (t-01…t-07) | чи є в diff тест, що саме так перевіряє X, а не щось схоже | рядок тесту з перевіркою | перевірка залежить від того, чого diff не показує (визначення змінної, інший файл) |
| «У коді є поведінка Y» (t-04, t-05, t-07) | чи diff додає саме Y за формулюванням критерію | рядок коду з умовою або повідомленням | поведінку видно лише після запуску команди |
| «Файли Z не змінено» | чи є в diff зміни поза дозволеними файлами | перелік файлів з заголовків diff | — (diff завжди це показує) |
| «Речення правильно описує команду» (t-08) | чи твердження збігається з довідкою про скрипт | цитата з README і цитата з довідки | довідка не містить потрібного |

Правила з промпту: `fail` ставиться і тоді, коли критерій вимагає того, що мало б бути в diff, а його там немає; `unknown` — коли даних бракує; вгадувати заборонено; `evidence` порожній лише для `unknown`.

## Чесні обмеження

- 42 випадки — це більше мінімуму курсу (10), але **не статистично достатня вибірка**.
- Порогу «каппа від стількох — добре» не наводжу: первинного джерела з порогами немає.
- **Обидва числа завищені.** Критерії й розмітку писала одна сторона (агент), суддя читає ті самі формулювання; розмітка перекошена (35 pass, 4 fail, 3 unknown), тож кілька помилок судді змінюють мало; артефакти однорідні (8 задач одного репозиторію, більшість патчів — тести).
- Каппа порахована на **моїх** задачах; на іншому наборі суддя може повестися інакше (Norman та ін.: рейтинги суддів зсуваються між бенчмарками).
- Фейлів у вибірці лише 4, і вони з двох типів (порожній тест, неточний опис). Слабкі місця судді, яких тут немає, калібрування не показало.
- **Що суддя точно не перевіряє:** він не запускає команди й не читає файли поза diff і `context`. Тому не знає, чи тести проходять (це робить брама `tests`), чи зміна справді вирішує задачу; про код, якого немає в diff, він каже `unknown`, і брама тоді червона.
- Критерії приймання написані людиною-автором (агентом) *після* знайомства з патчами; для нових задач їх мають писати до прогону виконавця.
- Верифікатор бачить diff, довідку й текст завдання — лише їх і відправляє. Файли секретів із diff викидаються, схожі на ключі рядки маскуються (`prepareDiff`), файли секретів у `context` заборонені перевіркою.
- Брама `verify` поки **не входить до обов'язкових перевірок** `main`: набору правил на `main` ще немає (див. [`gates.md`](gates.md), розділ 2). Скипнутий через `if` job рахується GitHub успішним для обов'язкових перевірок, тож її можна буде додати до переліку.

## Як запустити

```bash
# у CI — автоматично на harness/t-NN…; вручну на гілці прогону (ключ передає людина)
npx tsx --env-file=<файл секретів> scripts/harness/verify-task.ts --task t-08 --head <sha>
# калібрування
npx tsx --env-file=<файл секретів> scripts/harness/verify-task.ts --calibrate docs/lab3/verifier/labels.jsonl
npx tsx scripts/kappa.ts docs/lab3/verifier/labels.jsonl docs/lab3/verifier/judge-run.jsonl
```

У `package.json` скрипт `npm run verify` лишився від Лаб. 2 (`scripts/verify.ts` для spec.md): змінювати `package.json` без дозволу власника не можна, тож харнес викликається через `npx tsx`.
