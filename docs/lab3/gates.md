# Брами — Лабораторна 3, крок 01

Ланцюг детермінованих перевірок у [`gates.yml`](../../.github/workflows/gates.yml): `types → lint → tests → build`, плюс задача `record` (свідок). Кожна наступна брама має `needs` на попередню: поки типи червоні, решта не запускається (`skipped`), і це видно в прогоні, а не лише в логах.

## 1. Таблиця брам

Час — з реального зеленого прогону [`42494757211`](https://github.com/rsukhai/sentari/actions/runs/42494757211) (гілка `lab3/01-gates`, ubuntu-latest, node 24); `timeout-minutes` — ліміт у workflow.

| Брама | Що доводить | Чого коштує | Що пише |
|---|---|---|---|
| `types` | Код компілюється під `strict`: немає неіснуючих полів, невідповідних сигнатур | 58 с (включно з холодним кешем npm), ліміт 5 хв | `verdict` у `$GITHUB_OUTPUT`, артефакт `gate-types` (`types.log`) |
| `lint` | Дотримано правил лінтера (стиль, відомі пастки) | 34 с, ліміт 5 хв | `verdict`, артефакт `gate-lint` (`lint.log`) |
| `tests` | Поведінка збігається з очікуваною: Vitest, 199 тестів, без мережі й платних API | 30 с, ліміт 10 хв | `verdict`, артефакт `gate-tests` (`tests.log`, `docs/lab3/runs/**`) |
| `build` | Застосунок збирається (`next build`), тобто код придатний до запуску, а не лише до перевірки типів | 28 с, ліміт 15 хв | `verdict`, артефакт `gate-build` (`build.log`, `.next/BUILD_ID`) |
| `record` | Свідок: вердикти всіх чотирьох брам зведено в один файл, незалежно від того, де ланцюг урвався | 8 с, ліміт 5 хв | артефакт `gate-record` (`gate-record.json`: `gates`, `confirmed_by_output`, `sha`, `ci_run_url`) |

Чого ці брами **не** доводять: що зміна робить те, про що просили. Зелені чотири брами означають «не зламано», а не «правильно». Для цього — верифікатор останньою брамою (крок 02).

Порядок за ціною й визначеністю, але в цьому прогоні `types` найдовша (58 с проти 28–34 с): вона першою платить за холодний кеш і `npm ci`, наступні беруть кеш. Тобто порядок тут обґрунтований тим, що типи ловлять найбільше за найменше «осмислених» секунд (помилка типу видно за секунди після `npm ci`), а не абсолютною швидкістю задачі.

### Рішення в workflow, які варто знати

- **Вердикт беру з `needs.<job>.result`, а не з `outputs.verdict`.** На впалій брамі крок `echo verdict=pass` не виконується, тож `outputs` порожній; `result` є завжди. `outputs` лише підтверджує зелений (`confirmed_by_output`). Червоний ніколи не читається з `outputs`.
- **`record` бачить усі чотири брами.** `needs` показує лише прямі залежності, тому в `record` перелічено `[types, lint, tests, build]`, а не одну останню.
- **`if: ${{ !cancelled() }}`, а не `always()`:** зависла брама має право скасуватися. Дужки `${{ }}` обовʼязкові, бо вираз починається з `!`.
- **`timeout-minutes` у кожної задачі:** без нього діє типове значення 360 хвилин.
- **`concurrency` з `cancel-in-progress`:** новий push у ту саму гілку скасовує попередній прогін.
- **`pipefail`:** `shell: bash` явно, бо тоді GitHub вмикає `-o pipefail`, і `npm run … | tee` повертає код `npm`, а не `tee`. Червоний прогін нижче це підтверджує: без цього `types` лишилась би зеленою.
- **Версії дій перевірено в GitHub:** `checkout@v7`, `setup-node@v7`, `upload-artifact@v7`, `download-artifact@v8` (різні мажори в upload/download — не описка).

## 2. Обовʼязкові перевірки

**Стан: НЕ ввімкнено.** Станом на 2026-11-08 `main` не має ні набору правил, ні класичного захисту гілки (`gh api repos/rsukhai/sentari/rulesets` → `[]`). Тож ланцюг поки що рекомендація, а не брама: червону гілку технічно можна злити.

Причина відкладення: імена перевірок `types`, `lint`, `tests`, `build` зʼявляються в PR лише тоді, коли `gates.yml` лежить у базі PR. Поки `main` його не має, обовʼязкова перевірка вічно «очікується» і блокує навіть злиття Лаб. 2. Правило вмикається після злиття `lab3/01-gates` у `main`.

Що буде застосовано (потребує окремого дозволу власника репозиторію): набір правил на `main`, правило «Require status checks to pass before merging» з чотирма контекстами `types`, `lint`, `tests`, `build`, «Require branches to be up to date» залишено типовим (увімкнено).

## 4. Зв'язок із фабрикою

Прогін t-07 ([`t-07-1794151744271`](runs/t-07-1794151744271), гілка `harness/t-07-r2`) перезапущено від `origin/lab3/01-gates`, щоб його гілка містила `gates.yml`. CI-прогін [`42496262747`](https://github.com/rsukhai/sentari/actions/runs/42496262747) на коміті `7939c89e` усі чотири брами пройшов; `apply-gates.ts` знайшов `run.json` за збігом `branch_commit == sha` і записав `gates` та `ci_run_url`. Артефакт прогону тепер повʼязаний із вердиктом CI, а не лише з прийманням `acceptance_passed`.

Обмеження, яке вже видно: гілки `harness/t-01…t-08` з кроку 00 створено від `origin/main` без `gates.yml`, тому CI-вердиктів про них брами не дають (на них біжить лише старий `ci.yml`). Для них поле `gates` у `run.json` лишається `{}`. Це чесний стан, а не пропуск: робити задним числом нічого не буду, нові прогони фабрики йдуть від бази з `gates.yml`.
